# family-budget
# 🏠 林北小財庫 (Family Budget App)

這是一套專為現代家庭量身打造的跨平台、高客製化、即時同步的共同記帳系統。

-----

## 壹、 開發記帳 App 背景與目標

**「為什麼我們要自己開發記帳 App？」**
這是許多人在看到這套系統時的第一個疑問。市面上的記帳軟體多如牛毛，但我們面臨了一個無法妥協的痛點：**手機系統的跨平台障礙**。
家人之間使用的手機作業系統不同（Android 與 iOS 並存），導致市面上絕大多數的記帳 App 無法實現完美的雙平台無縫共享與即時同步。此外，每個家庭的消費習慣、商家分類、付款方式（如特定的行動支付綁定特定的信用卡）都不盡相同，現成軟體僵化的設定根本無法滿足我們對「客製化」與「自動化防呆」的高度需求。

為了解決這個問題，我決定親自研發這套「林北小財庫」。
**核心目標**：
1. **打破系統藩籬**：採用 React + Firebase 雲端架構，只要有瀏覽器（Safari 或 Chrome），不論蘋果或安卓手機都能完美運行並即時同步。
2. **極致的客製化與自動化**：從主頁顏色、消費分類、自訂商家，到「選擇某項目自動帶入商家與特定信用卡」的連動規則，全都能由家庭成員自行定義。
3. **直覺的家庭共享**：建立「房間」概念，家庭成員輸入通關密碼即可加入，並具備資料隔離（僅限本人修改）的安全機制。

## 貳、 記帳 App 操作使用手冊及核心邏輯概念

本系統設計以「低阻力輸入、高動態回饋」為核心，以下為各模組的詳細操作指引與底層自動化運作邏輯：

1. 基礎記帳步驟指南
當使用者點擊首頁底部橘色的「＋」號時，系統會開啟全螢幕的記帳工作流表單，頂部提供「支出」、「收入」、「轉帳」三個分頁標籤，其各自擁有獨立的輸入欄位與驗證機制：
⚠️ 共同核心步驟（金額運算）： 進入表單後，首要步驟為點擊巨大的「金額區塊」，這會自動喚醒內建的「安全沙盒計算機」。使用者可直接在畫面上進行 + - × ÷ 及括號的複合式運算（例如：買菜 120 + 85 * 2），確認無誤後點擊「確認金額」，系統會自動將運算結果進行 Math.floor 取整數並帶回表單，有效解決一邊切換手機計算機一邊記帳的破碎體驗。

🌸 支出（Expense）記帳流程：
選定日期與頻率：預設為今天。若補登過去帳目，點擊日期會開啟原生選擇器（若非今日，系統會亮起紅色閃爍警示標籤）。
分類項目雙層選擇：先於「主分類」下拉選單選定大項（如 🍔 飲食），右側的「項目清單」會自動動態渲染出該分類專屬的子項目（如 早餐、午餐、飲料）供精準勾選。
觸發自動帶入規則：當選定項目後，系統會自動在背景查詢該房間的 autoFillRules。例如選定 早餐，下方的「商家」會秒級自動帶入 早餐店，省去手動選擇的繁瑣。
觸發付款方式規則：當「商家」被帶入或由使用者調整後（如改選為 麥當勞），系統會立即觸發第二層監聽（methodRules），自動將付款方式切換為 信用卡 並帶入子帳戶 點點卡。
確定花費對象與存檔：透過多選藥丸標籤勾選這次是為誰花錢（可單選或複選）。確認無誤後，可選填備註或啟動相機拍照，最後點擊「儲存紀錄」，即可透過 writeBatch 秒級寫入雲端。

💰 收入（Income）記帳流程：
切換至收入頁籤，選擇「收入分類」（如 薪水、獎金）。
勾選對象（可複選，用以統計該筆收入歸屬）。
於「存入帳戶」區塊選擇這筆錢實體存進了哪裡（如：銀行 ➜ 元大銀行），儲存後系統會自動為該銀行帳戶增加對應資產。

🔄 轉帳（Transfer）記帳流程：
用於帳戶間的資金移動（如：提領現金、手動繳信用卡費）。
選擇「轉帳分類」（如 信用卡繳款）。
依序配置 「📤 轉出帳戶 (扣款)」 與 「📥 轉入帳戶 (存入)」 的雙層選單。
儲存後，系統會同步對轉出帳戶執行扣款、對轉入帳戶執行存入，此流向不計入家庭的損益盈虧。

2. 財務總覽與統計報表查閱
📊 導覽至帳戶總覽： 點擊首頁左下角「帳戶」按鈕進入。頂部看板會即時加總顯示整體的「淨資產」、「總資產」與「總負債」。下方將資產結構切分為「現金」、「銀行/電子票證」與「信用卡刷卡（累積未繳卡費）」三大區塊。
查看歷史明細抽屜：點擊任一實體帳戶卡片（如：國泰世華），會從底部拉出該帳戶的歷史明細。此處完美應用了「真實存摺滾動算法」，每一筆記帳右側都會顯示歷經該筆消費後「當下的合計金額」，方便與真實的網路銀行或錢包皮夾直接進行對帳。
📈 導覽至統計分析： 點擊首頁右下角「統計」按鈕進入。
進階多重條件篩選：頂部可切換觀看支出、收入或轉帳。點擊「分析選單」可啟動多維度複選，您可以同時勾選分類、項目、商家與付款方式。
交叉分析與動報表：系統會自動將您勾選的條件結合成複合式標籤（如：飲食 - 項目:飲料 - 商家:50嵐），並渲染出高動態的 SVG 圓餅圖。點擊圓餅圖上任一色塊，底部會立刻拉出該篩選條件下的具體消費流水帳清單。

3. 後台設定與規則配置指引
點擊首頁右上角「齒輪」圖示進入設定中心，此處主控整個房間的 DNA 結構：
分類與自訂清單維護：在頁籤中選擇支出、收入或轉帳，可透過 SettingBlock 對主分類、商家、信用卡或銀行清單進行即時維護。若要維護主分類底下的「子項目清單」，只需在下拉選單選定該主分類（如 🚗 交通），下方即會彈出專屬的子項目增刪區。
自動化規則（AI 連動）配置：
商家預設規則：在下拉選單選擇「當項目為 加油 時 ➜ 自動帶入商家 加油站」，點擊新增。
付款方式預設規則：選擇「當商家為 加油站 時 ➜ 自動帶入付款方式 信用卡(玉山銀行)」，點擊新增。
權重優化：建立多條規則後，可利用右側的 ↑ / ↓ 按鈕調整規則鏈的排序，排序愈上方的規則在記帳時擁有愈高的自動帶入權限。
跨房間自動傳送配置：在「其他」頁籤中可開啟 promptCashSync（支出自動跨房間提示）。開啟後，還能進一步配置白名單，勾選「排除提示的花費對象」，讓特定個人的私有花費不會觸發跨房彈窗，兼顧便利與隱私。

4. 系統核心防呆與貼心設計矩陣
非今日時間戳防錯標籤：記帳日期只要不等於本機當天，表單會立刻激發亮紅色的 非今日 動態閃爍標籤，強力提醒使用者正在補過去的帳目，防止日期誤植。
藥丸標籤智慧互斥邏輯：在選擇花費對象時，若點擊 全家，系統會自動將個人標籤（老公、老婆等）清空；反之若點擊了個人，則會自動退選 全家，從視覺和邏輯上阻斷矛盾的資料產生。
子項目與規則溯及既往：當使用者在後台修改了某個常見商家或信用卡名稱時，系統不只修改設定，還會啟動後台批量異動，自動把過去幾千筆歷史紀錄中的舊名稱同步更新，確保歷史報表不會因為改名而破裂。

📌 總結：
房間與成員管理：基於動態代碼與 PIN 碼的隔離環境，具備本機快取多房快速切換與本人資料鎖定修改權限。
智慧防呆記帳表單：內建安全運算沙盒、前端畫布縮圖優化、以及「項目 ➜ 商家 ➜ 付款帳戶」的高智慧雙層連動自動帶入引擎。
完美存摺式帳戶總覽（核心會計邏輯）：背景採用「消費日期」由舊到新正向流動計算結餘，前台採用最新到最舊降冪渲染，完美契合真實存摺閱讀習慣的極致設計。

## 肆、 研發歷程與常見錯誤檢討 (Developer Insights)
在經歷了多次的架構更迭與敏捷開發後，我們將曾遭遇過的隱蔽 Bug 與技術陷阱完整記錄，作為後續研發與系統重構的最高防禦手冊：

🚨 錯誤點一：週期性排程的「雙胞胎幽靈紀錄」
錯誤現象：在表單建立新的週期性支出（如每月房租），或是將週期性明細「跨房間傳送」時，存檔的瞬間會在起始當天產生兩筆一模一樣的重複明細。
發生原因：handleSave 或 handleSendToOtherRoom 在主線程中會先寫入一筆使用者當下配置的紀錄。隨後，調用 generateFutureDates 產生未來日期陣列。然而，該函數內部為了時間軸的完整性，回傳的日期陣列預設包含了起始當天，導致隨後的批次寫入迴圈（forEach）又把當天重複寫入了一次。
解決與防範：凡是從日期產生器拿到的未來日期陣列，在進入雲端批次寫入（Write Batch）迴圈前，必須強制掛上過濾器：.filter(d => d > record.date)，精準剃除起始當天，交由主線程單一寫入，徹底消滅幽靈雙胞胎。

🚨 錯誤點二：Vercel 生產環境編譯崩潰 (Syntax error: '}' expected)
錯誤現象：本機端（Development Mode）運行完全正常，但一推送到 GitHub 觸發 Vercel 線上自動部署時，會卡在 react-scripts build 階段並拋出 Failed to compile，回報特定行數語法錯誤。
發生原因：
為了維持元件的單一純粹，我們在 SharedUI.jsx 裡使用了大量的 Tailwind CSS 類別。當單行字串過長（長達 300+ 字元）且內部夾雜了複雜的 JavaScript 三元運算子與模板字串 ${} 時，Vercel 的遠端 Babel 編譯器會因為解析超載而誤判。
在深層巢狀的 HTML 屬性或類別拼接中，發生了極細微的括號誤植（如將 ) 錯打成 ]）。
解決與防範：撰寫 Tailwind CSS 時應適度進行「換行拆解與常數提取」，避免單行代碼無限延伸。當 Vercel 部署失敗時，應第一時間查閱 Log 的 Syntax error 提示，並嚴格落實括號對稱檢查。

🚨 錯誤點三：帳戶明細「顯示排序」與「結餘計算」的逆向衝突
錯誤現象：當使用者補登過去的帳目（例如在 6/18 補記一筆 3/1 的現金消費），該帳戶的結餘合計數字會全數算反，導致明細卡片上的金額與實際金額嚴重脫鉤。
發生原因：原先的代碼直接對經過篩選、且已經為了前端閱讀而調整為「新到舊（降冪）」的陣列執行結餘累加。這導致系統在背景會拿「今天」的餘額去扣「昨天」的消費，完全違反了時間軸的正向推移。
解決與防範：必須實施「計算與渲染徹底分離」架構。在 AccountsView.jsx 中，計算结餘時先對全庫歷史紀錄進行過濾，接著執行第一次排序：嚴格依據「消費日期(date)」由舊到新（升冪）排列，並從初始餘額順向累加。結餘數字精確綁定到紀錄物件後，才執行第二次排序：由新到舊（降冪）排序輸出給前端 UI 渲染，完美重現銀行存摺邏輯。

🚨 錯誤點四：信用卡負債分錄之正負號會計錯誤
錯誤現象：在「帳戶總覽」中，每次記一筆信用卡消費，信用卡的負債從小計上看反而變少了；而執行轉帳還卡費時，負債金額反而飆高。
發生原因：信用卡在系統中屬於「負債欄位」，其資產增減邏輯與液態資產（現金、銀行）完全相反。現金支出是 餘額 - 金額，但信用卡支出（刷卡）應該是 累積卡費 + 金額（代表負債增加）；轉帳還款時，則是信用卡負債減少。原先代碼一律套用資產扣除公式，導致會計分錄倒置。
解決與防範：在 balances 計算矩陣中，明確加入 key.startsWith('cc_') 條件判斷。若是信用卡帳戶，支出時金額轉為 +amt，收入或轉入時轉為 -amt，確保負債小計能精確反映應繳卡費。

🚨 錯誤點五：自訂下拉選單外部點擊監聽器造成的記憶體流失 (Memory Leak)
錯誤現象：App 在手機上開啟運作一段時間後，每次點擊選單或切換頁面會愈來愈卡頓，甚至導致手機瀏覽器崩潰閃退。
發生原因：CustomDropdown 元件為了實作「點擊選單外部自動關閉」，在 useEffect 中向全域 document 註冊了 mousedown 事件監聽器。然而，當組件因為頁面切換而遭到銷毀（Unmount）時，沒有在生命週期結尾移除該監聽器。這導致每次開關選單，全域就會多出一個無效的監聽器，瘋狂吞噬手機記憶體。
解決與防範：嚴格落實 React 資源回收機制。在所有註冊全域監聽（如 window.addEventListener 或 document.addEventListener）的 useEffect 中，必須在 return 閉包中明確調用 removeEventListener 進行解鎖銷毀，保證記憶體零流失。

🚨 錯誤點六：非預期輸入字元造成計算機 eval 執行緒死鎖
錯誤現象：在小鍵盤計算機輸入算式時，如果不小心按到連續的運算子（如 5++ 或 6×÷）或未閉合的括號，計算機畫面會直接卡死，點擊任何按鈕都失去反應。
發生原因：底層在解析算式時使用了 new Function 的類 eval 機制。當算式語法不合法時，核心 JavaScript 引擎會直接拋出語法錯誤（SyntaxError），若沒有對此錯誤進行攔截，整個 React 的渲染線程（Render Thread）就會當場當機。
解決與防範：在 utils/helpers.js 的 evaluateCalc 函數中，全面使用 try...catch 沙盒塊將運算核心包裹起來。並在進入運算前，透過正規表達式先篩選掉非法的連續算符，一旦捕獲到錯誤，立即中止運算並優雅回傳原字串，確保前台死鎖悲劇絕不發生。

🚨 錯誤點七：行動裝置獨立分頁自動重整（Auto-Refresh）造成的狀態丟失
錯誤現象：當使用者在填寫備註很長的表單，或是正在設定複雜的統計過濾條件時，中途切換去 LINE 回覆訊息，再切換回記帳 App 時，畫面自動重新整理，剛剛填寫的所有內容瞬間消失。
發生原因：行動裝置（尤其是 iOS 的 Safari 或記憶體較小的 Android 機型）為了節省系統資源，當瀏覽器退到背景時，隨時會回收 React 的記憶體狀態（State）。當使用者切換回來時，網頁會被強制刷新，導致記憶體中的狀態全數歸零。

解決與防範：未來針對大型表單（如 RecordFormView）或全域核心設定，應逐步引入「本機快取隔離機制」。在狀態變更時同步寫入 localStorage，並在組件載入時優先讀取快取，直到點擊「儲存」後才清空快取，全面對抗手機系統的資源回收機制。

## 伍、 針對此 App 的總結與未來建議
「林北小財庫」的誕生，成功解決了不同手機系統間難以共享財務數據的痛點，並透過高度的防呆連動設定，將家庭記帳的阻力降到了最低。系統底層對於非同步寫入、離線快取與時序邏輯的處理已趨於成熟穩固。

**🚀 未來發展與擴充建議：**
1. **PWA (Progressive Web App) 升級**：目前為網頁版應用，建議未來可在專案中加入 `manifest.json` 與 `Service Worker`，讓 iOS 與 Android 使用者都能將其「加入主畫面」，獲得如同原生 App 般全螢幕、無網址列的順暢體驗。
2. **年度預算系統 (Budgeting)**：利用現有的分類設定，為每個主分類擴充「每月/每年預算上限」欄位，並於統計分析頁面加入預算達成率的視覺化進度條。
3. **發票收據 OCR 自動辨識**：我們已經實作了高效的前端相機圖片壓縮機制。未來可考慮串接 Google Cloud Vision API，讓系統自動掃描照片中的總金額與商家名稱，實現「拍照即記帳」的極致自動化。
